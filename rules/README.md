# AI 规则与执行机制总入口

原生 Codex↔DSH 连接验证另见 [协作询问规则](native-bridge/interaction.md)与[设置说明](../docs/development-history/APPROVAL_AND_QUESTIONS.md)。仅由显式配置脚本发送给指定验证 Session，不由旧 Studio 的 leadRule 自动加载，不替代下列实际角色规则。

这是程序规则入口；全仓资料查[文档地图](../docs/README.md)。职责、操作方法、工具参数和程序约束的维护分工见[维护约定](../docs/MAINTENANCE.md)。本轮文档整理未改写实际角色文本，也未启用新Skill。

工作台入口：**设置 → AI 规则与技能**。这里可以查看主策划、主开发和DSH实际基础规则，并编辑两位负责人的补充要求。

| 位置 | 用途 | 如何修改与生效 |
|---|---|---|
| roles/planner.md | 主策划实际基础角色规则 | 专业维护时修改；保持职责、安全与工具兼容。基础规则会进入后续对话/恢复，不打断当前Turn |
| roles/developer.md | 主开发实际基础角色规则 | 同上，包含拆包、委派、复核和协作约定 |
| roles/dsh.md | DSH执行者实际基础规则 | 维护端审查后修改，新建执行任务加载；现有Session保持原配置 |
| preferences/planner.md | 制作人给主策划的补充要求 | 可在网页编辑；保存后下一次正常对话发送，不立即调用模型 |
| preferences/developer.md | 制作人给主开发的补充要求 | 同上，适合汇报格式、工作习惯与专业侧重点 |
| skills/README.md | 专用Skill维护入口及实际启用情况 | 当前未注册自动加载的Studio专用Skill；不能放入文件就声称启用 |
| harness/README.md | 程序执行机制与源码入口 | 是说明和导航，不是可改文字就改变执行的配置 |

基础规则由原源码逐字迁移，不是供人参考但程序不读的镜像。界面显示完整基础规则、补充要求、路径与生效记录。空补充表示仅使用基础规则。

适合直接写的例子：“汇报先说明游戏效果、已验证结果和下一步，技术日志折叠展示”。不要把API Key、凭据或私人数据写入规则，这些文本可能进入模型上下文并随源码管理。

保存补充会先把旧文本备份到app/runtime/rule-backups，采用内容版本校验，冲突时不覆盖。后台记录变更指纹；原Thread、历史和在途工作不变。外部编辑器修改的内容也会在后续发送时读取，但不会自动产生网页保存审计。回退时读取旧文本重新保存，保留历史记录。

“已随对话指令发送”仅证明Studio提交了文本，不证明模型每次都遵守。旧历史不改写。与既有安全、产品授权冲突的要求不得执行；本目录不授予工程、Shell、网络或系统权限。

## 主开发分层（2026-10-25）

[主开发角色](roles/developer.md)只说明职责、判断和汇报方式；[工具协议与执行边界](protocols/developer.md)独立保存调用约定。两份由leadRule在每次正常Turn合并提供，缺协议则拒绝发送。网页角色区默认展示职责，协议折叠查看；内容hash覆盖两份和补充要求。不是仅放入目录但模型未读取的说明。

## 主策划分层（2026-10-25）

[主策划角色](roles/planner.md)负责设计质量、文档交接、规则一致性和专业审查；[工具协议](protocols/planner.md)保存读取、协作、交付与执行边界。与主开发同样由leadRule合并提供，协议缺失拒绝发送，网页独立折叠查看。DSH研发委派和技术测试由主开发负责，主策划不是所有任务的转述者。源码更新须部署后才支持两位负责人的分层协议，实际生效以界面加载指纹为准。
