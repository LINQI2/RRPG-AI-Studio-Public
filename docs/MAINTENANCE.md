# 文档维护与事实来源

## 借鉴 RRPG 的逻辑

只读参考了正式 RRPG 的 README、AGENTS、AI_CONTEXT 和 Docs/文档地图：入口只导航，按问题定位资料，设计意图、确定规则、当前实现、阶段证据各有职责。Studio 是研发工具，不复制 GameDesign/GameSpec 等游戏目录，也不引入一套新的审批流程。

## 哪份资料负责什么

| 问题 | 应使用的依据 | 不能拿什么替代 |
|---|---|---|
| 本轮允许做什么 | 制作人的明确授权及现有安全边界 | 路径配置、旧报告或 AI 自述 |
| 产品应该怎样工作 | PRD 和已确认的产品决定 | 某次测试夹具或现有缺陷 |
| 程序现在怎样工作 | 对应源码、配置、运行版本与实测 | 架构目标或尚未部署的改动 |
| AI 实际收到什么规则 | rules 源文件、加载代码和发送记录 | 面向人的说明、文件存在或模型口头承诺 |
| 某功能验证过没有 | 具体版本、用例、原始结果及验收范围 | API 接受、模型结束、旧版通过或任务状态 |
| 现在正在执行吗 | 当前工作台与原生执行记录 | 日期化报告中的“当前” |

冲突时先说清是在比较“要求”和“实现”，还是两份记录的时间/范围不同。源码存在缺陷不取消需求；新报告也不自动覆盖产品决定。能用事实核对的技术差异由维护者处理，只有无法解决的产品取舍、权限或重大风险才交制作人。

## 写在哪、更新什么

- 长期需求更新根 PRD；技术职责更新 ARCHITECTURE；使用步骤更新 app/docs 对应手册。
- 阶段计划、调查、验证、失败和交付记录写入 `reports/YYYY-MM-DD-主题/`，标明“计划 / 调查 / 已实施 / 已验证”及证据范围；默认只在本机保留，不整包提交日志或快照。
- 当某阶段形成长期结论，将必要结论同步到对应现行文档，原报告保持可追溯。不是每完成一个小修改都新增一份总规划。
- [STATUS](STATUS.md)只维护简短、带日期的接手事实和未完成项，不复写所有运行事件；[IMPLEMENTATION_PLAN](../IMPLEMENTATION_PLAN.md)负责后续工作入口。
- 角色职责、操作方法、工具参数和程序约束分层维护。主开发现已将职责与protocols/developer.md分离并一并加载；主策划也已分层，DSH未调整。以后拆分必须适配实际加载，不能把要求搬到模型无法读取的文件后宣称生效。
- 新增或改名文档时更新地图/清单，检查相对链接。被外部引用、程序读取的路径优先保留；真要迁移须更新调用方并提供旧入口跳转。

新文档开头简要说明：用途、状态、适用范围、核对日期、相关依据。当前指南写可重复操作；历史报告写当时做了什么。不要让“最新交接”承担所有长期知识。

## 查阅和搜索

先查地图，再在选定范围搜索。根目录全量递归容易吞入原生会话、备份和重复证据；默认不搜 runtime、workspaces、archive、node_modules。

```powershell
# 在 Studio 根目录：只搜索现行说明和规则
rg -n "关键词" README.md PRD.md ARCHITECTURE.md IMPLEMENTATION_PLAN.md docs rules app/docs
# 查实现：限定源码与测试
rg -n "关键词" app/src app/tests
# 查一次历史原因：先由证据目录选中具体日期目录
rg -n "关键词" reports/2026-10-24-task-detail-review -g '*.md'
```

runtime 中的原始回执仅按具体任务/执行标识读取并脱敏；认证目录不属于常规文档搜索范围。链接到私有证据不意味着允许上传。
